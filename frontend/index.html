Details

Decision

One Postgres table for reports; flexible payloads live in a jsonb column. Authentication is wallet-signature based — no passwords, reusing the same keys as Arkiv.

create table reports (
  id          bigserial primary key,
  org_id      uuid not null,
  payload     jsonb not null,
  report_date date not null,
  created_by  text not null,      -- wallet address
  created_at  timestamptz not null default now()
);

Why

  • Report shapes change weekly; one table keeps migrations small.
  • jsonb with a GIN index measured 120 ms p95 on 2 M rows.
  • Wallet signatures reuse the Arkiv identity — one key for chain and app.

Auth flow

  1. Server issues a single-use nonce.
  2. Client signs "atlas-login:<nonce>" with its wallet.
  3. Server recovers the address and replies with a signed token.

02 — Pipeline

How a commit moves.

Five steps from a one-line note to an entity any member can pull — the same code path runs in the CLI, the MCP server, and this page.

  1. 01

    Build

    The body {summary, details, tags} is wrapped in a versioned envelope with the branch, parent hash, author, kind, and timestamp.

    envelope v1 · kind decision · agent claude-code
  2. 02

    Encrypt

    The body is sealed with XChaCha20-Poly1305 using the repo's 32-byte group key and a fresh 24-byte nonce. Only key holders can read it.

    xchacha20-poly1305 · repo group key
  3. 03

    Hash

    sha256 over the canonical JSON of the hash fields — sorted keys, no whitespace. Change one byte of ciphertext and the hash moves.

    sha256(canonicalJson(payload))
  4. 04

    Sign

    The wallet signs the commit hash with signMessage. The signature travels inside the envelope; anyone can recover the signer.

    sig = signMessage(commitHash)
  5. 05

    Write

    One Arkiv entity — payload plus public attributes — with an expiry set by kind. The branch head is patched to the new hash in the same breath.

    entity + attrs · patch branch head

Verification, in order

  • BAD_HASH recomputed hash ≠ envelope hash
  • BAD_SIGNATURE recovered address ≠ envelope author
  • OWNER_MISMATCH entity owner ≠ author — someone else's key wrote it
  • NOT_MEMBER author not in the repo member list
passes all four → decrypt, show, hand to agents
× fails any → red badge, reason shown, never decrypted

03 — Features

Three features, nothing else.

The whole build is scoped to upload, pull, and show — so the demo stays honest and the tool stays small.

F1 · commit

Commit context from anywhere.

One command seals the body, signs the hash, and writes the entity. Expiry is chosen by kind, so scratch pads fade and milestones stay a year.

Teammates pull it verified.

Pull renders a branch's history as markdown, oldest first — invalid entries are counted and skipped, never handed on.

Agents do the same over MCP: context_pull(branch) before starting work.

F3 · view

The whole history, one page.

Rail of branches, graph in time order, commit list, and a proof panel per commit. The group key never leaves the tab.

Re-verifies every envelope client-side each refresh cycle.

Why Arkiv

A ledger, not a database you have to trust.

  • expiry Entities carry an on-chain expiry in blocks. Context decay is enforced by the network, not a cron job.
  • queries Attributes are public and queryable — find a repo's commits by type, repo_id, branch, kind without an indexer.
  • ownership An entity's owner is its writer's wallet. Authorship is a protocol fact, checked in the verify chain.
  • branch heads Heads are patched attributes. Single-writer by construction: only the owner's wallet can advance them.

05 — CLI

The whole CLI.

Eight commands, one per concept: repo, member, branch, commit, pull, log. Node 22+, no runtime dependencies.

cogit init <name> create a repo and main, write .cogit/config.json
cogit invite <addr> add a member, print a cogit1: invite carrying the group key
cogit join <invite> save the invite to config, mode 600
cogit branch <name> fork from the current head — every writer gets a branch
cogit use <branch> switch the current branch
cogit commit -m "…" encrypt, sign, write the entity, advance the head --kind--tag--details-file
cogit pull <branch> verified markdown, oldest first → stdout and .cogit/context/
cogit log commits with verified / invalid status --branch

06 — Questions

Asked often, answered plainly.

Who can read a commit?

Anyone can find the entity — its attributes (repo, branch, kind, author, timestamp) are public on Arkiv. The body is XChaCha20-Poly1305 ciphertext; only holders of the repo group key can read it. Managers share the key with cogit invite / cogit join.

Can a teammate rewrite my branch?

No. A branch head is a patched entity attribute, and Arkiv only accepts patches signed by the entity's owner. A forged commit shows up as OWNER_MISMATCH — red in the viewer, skipped by pull.

Why do commits expire?

Agent context loses value fast. Scratch notes last 3 days, notes 14, decisions 90, milestones a year — expiry is set per kind at write time and enforced by the network. Active branches extend their head's expiry on every update.

Where does the group key live?

On disk it sits in .cogit/config.json (mode 600), delivered once via an invite string. In this viewer it lives in memory for the lifetime of the tab and is never sent to a server — decryption happens in your browser.

What exactly does the green badge prove?

Four checks, in order: the hash recomputes, the signature recovers the stated author, the Arkiv entity owner equals that author, and the author is in the repo's member list. All four pass before you or your agent ever see plaintext.

Is there a server in the loop?

None. The CLI and the MCP server talk to the Arkiv RPC; this page reads the same RPC from your browser. There is no cogit backend to deploy, and no telemetry.
